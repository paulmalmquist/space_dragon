Pure candidate state owns the one pod reward. Animation, replay/skip and review cameras cannot grant extra rewards. A distinct Unity PlayerPrefs key isolates it from Babylon saves; incompatible saves are preserved, and storage failures report session-only progress. Review identified unsafe saved-position restoration and added collision-safe placement/recovery. Its EditMode test passes; the browser now restores the saved valid position and single reward. Incompatible/colliding checkpoint coverage remains the named EditMode coverage, not an observed corrupt-browser-save test.

The pipeline imports the uncompressed original pod **537,228 bytes**, SHA-256 `bbe39ee99797e309c51ab27ee4ef25a6636a40b09584a418f73bb2b95f8d95df`. Babylon uses its **463,644-byte KTX2 derivative**. Geometry, material meaning and animation are shared; file bytes/texture transport differ deliberately. Existing CC0 WebP surfaces are losslessly decoded to PNG; URP dielectric smoothness is packed from roughness. The same original HDR is imported, with a one-time sky-only reflection probe to match the rotated environment. [Prepared input receipt](../../unity/SpaceDragon/Assets/SpaceDragon/Imported/asset-receipt.json) records source/output hashes and transformations. No new media service, family likeness or editable Blender source is added to a player build.

The glTFast importer does not apply the source's `KHR_materials_emissive_strength`. Setup therefore clones the affected material and applies the original linear source factor times **1.847999930381775** strength, without editing the GLB/imported subasset or multiplying twice on rerun. The latest setup receipt records eight affected renderer slots and effective emissive factor approximately **(0.132, 1.474, 1.848)**. This restores source material meaning; it is not a new artistic emission choice.

## Final gzip-delivered browser measurements

Installed Chrome **156.0.8078.76** on the Lenovo/AMD device used actual **WebGPU**; its renderer string identifies ANGLE AMD Radeon (0x000015E7) / Direct3D11. Browser viewport was **1366 × 900**, with both CSS and render canvas **1280 × 720**, DPR 1. Each view ran ten seconds after settling/reset; statistics represent its final 300 post-warmup Update intervals, about five seconds. All three samples report zero intervals above 50 ms.

| View | Median / p95 / max ms | Estimated fps | Previous completed-frame draws | Unity used-memory counter / JS heap bytes |
| --- | --- | --- | --- | --- |
| Home | 17 / 18 / 19 | 60.00 | 265 | 73,332,263 / 35,980,076 |
| Arrival | 17 / 18 / 32 | 59.39 | 319 | 73,766,439 / 35,517,557 |
| Pod detail | 17 / 18 / 21 | 60.00 | 226 | 73,455,143 / 35,709,666 |

These separate memory columns must not be summed into a total-memory claim. WASM heap allocation is unavailable (`null`); neither counter measures total browser process/GPU memory. Frame intervals are wall-clock cadence, not GPU execution time. The short, near-vsync static views do not establish sustained gameplay or 1080p performance.

With a fresh browser context and HTTP cache disabled, all five initial responses were gzip encoded. The WebGPU run delivered **25,903,238 encoded body bytes** (**25,904,844 including observed response overhead**, HTML included). `createUnityInstance` completed in **3,048.3 ms**; controls were first observed ready at **10,055.8 ms**, including startup, the one-time reflection capture, reveal and 500 ms polling. OS/driver caches were not cleared. The underlying build remains **58,779,167 uncompressed bytes**.

The final forced WebGL2 run used the same canvas/device/build and gzip responses. Home, Arrival and Pod detail respectively measured **59.81 / 59.99 / 59.80 fps**, median **17 / 17 / 17 ms**, p95 **18 / 18 / 18 ms**, max **27 / 28 / 33 ms**, and zero spikes above 50 ms. Draw counters were again 265/319/226. Arrival recorded **64,521,767 bytes** on Unity's used-memory counter and **36,190,926 bytes** in the separately labeled JS heap; WASM allocation remained unavailable. Initial player load was **2,680.6 ms**, controls readiness **10,182.6 ms**, with the same **25,903,238 / 25,904,844 body/transfer bytes**. These short samples establish functional fallback on this device, not a WebGL2 performance advantage or broad browser compatibility.

The earlier raw-delivery passes remain archived with **58,779,167 body bytes** and their distinct timings: WebGPU player/controls **2,399.7 / 8,902.2 ms**, WebGL2 **2,318.6 / 9,327.2 ms**. They are historical evidence, not the final encoded-transfer comparison. The gzip server precompresses files before listening; it does not rewrite the game build or include first-request compression work in load timing.

This is a common-asset/camera feasibility comparison, not an engine-only benchmark of identical workloads or pixel-identical rendering.

Unity wall-clock Update intervals are not GPU timings. Optional profiler counters, WASM allocation and Chromium JS heap are labeled separately; none is total browser/GPU memory. Cold/warm caching, served bytes, actual graphics API/device and sample duration/window must accompany any performance figure.
